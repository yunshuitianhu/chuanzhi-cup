## 1. 缺失 GPS 的填充值被当作真实定位

**根因**：加载器为保持轨迹连续，对 `longitude/latitude` 执行 `ffill().bfill()`，同时在 `__observed_coordinates` 保存原始观测掩码；但聚类、空间支持度、地图轨迹/热力/采样点/Top5 与搜索中心只检查数值范围，没有消费该掩码。

**修复**：
- `detection_support.cluster_black_samples` 只对 `coordinate_mask` 为真的点聚类；缺 GPS 的预警点保留为 `cluster_id=-1`，点级预警与原始记录不丢失。
- `detection_support.spatial_support` 在缺 GPS 处断开空间支持度。
- `backend/routers/charts.py` 的 `trace_map`：轨迹、热力、采样点、聚类中心、Top5 和视野范围只使用原始有效 GPS；新增 `coordinate_note` 说明。
- `backend/map_samples.py` 不再为填充坐标生成地图采样点，`id` 仍保持原始行位置。
- `data_quality.coordinate_text` 遇到 `__observed_coordinates` 为假时返回 `None`；综合摘要与质控记录不再显示伪造坐标。
- `backend/routers/trace.py` 的默认/轨迹搜索中心、`app.py` 旧版 folium 地图同步过滤。
- `get_cluster_summary` 的中心/空间跨度只用有效 GPS；旧项目若聚类无有效定位，中心为 `null`，不构造虚假热点中心。

**回归**：`tests/test_code_review_20261028_regressions.py::MissingGpsSpatialTests`。7 行样本首尾有 GPS、中间 5 行缺 GPS 且氨氮 18 mg/L：原始有效 GPS 仍为 2，黑点仍为 5，但聚类热点为 0；地图轨迹/热力/采样点各 2，Top5 与聚类为空，缺失行坐标为 `null`。

**限制**：没有 `__observed_coordinates` 的旧项目/旧工作簿无法追溯哪些坐标是填充值，需要重新加载数据或重新分析；本次不猜测。

## 2. 卫星请求异常中的 Token 进入模型上下文

**根因**：`geo_tools.get_satellite_image` 把 `requests` 异常原文写入工具错误，而异常可能包含带 `token=` 的完整 URL；Agent 把工具原文直接追加到下一轮模型消息。此前的脱敏只覆盖最终错误、公开提示和证据快照。

**修复**：
- `geo_tools.get_satellite_image` 的异常分支只返回固定分类“卫星影像请求异常：网络连接或服务不可达”，不再拼接异常文本/URL。
- `backend/agent/loop.py` 在工具结果进入模型上下文前统一调用 `_scrubber()`；工具状态提示同样脱敏。证据快照原本已单独脱敏。

**回归**：`TokenRedactionTests`。受控假 Token + `ConnectionError`：工具结果不含 Token；Agent 第二轮模型请求消息中也不含 Token。

## 3. 旧 Streamlit 加载器丢弃有效 DO=0

**根因**：`app.py` 只共用了列名归一化，仍保留自己的“DO=0 当缺测”清洗和插值逻辑，没有生成与生产加载器一致的原始观测掩码，导致旧入口漏报。

**修复**：`app.py:load_data` 改为读取上传字节后复用 `water_quality_mcp.loaders.load_data`，统一列识别、DO=0 有效性、范围校验、插值标记、`__observed_*`/`__observed_coordinates`、数据身份与错误返回；解析成功后才重置旧分析状态。旧版地图也同步使用有效 GPS。

**回归**：`LegacyStreamlitLoaderTests`。3 行 DO=`[7,0,7]`：旧入口现在保留 `[7,0,7]` 且 `__observed_dissolved_oxygen` 全为真，与生产加载器一致；两者均检出 1 条预警，不再漏报。

## 4. MCP 重新加载数据后保留旧分析结果

**根因**：`tool_load_data` 成功时只赋值 `state.df`；`tool_extract_video` 也只替换帧，旧的 `black_spots`、交叉印证、站点结果和河道模型仍可被后续摘要/图表消费。

**修复**：
- `WaterQualityState.replace_data` 统一清空 `black_spots`、`video_frames`、`cross_validation_result`、`national_station_result` 并记录新文件名；解析失败不调用。
- `WaterQualityState.replace_video` 只清空依赖旧视频的交叉印证，保留监测数据与黑点。
- `tool_load_data` 成功后同时 `reset_river_state()`，避免旧河道模型与新数据混用。

**回归**：`McpReloadTests`。载入正常新表后黑点/视频/交叉印证/站点结果均为空，河道单例被重置；解析失败保留旧状态；替换视频只失效交叉印证。

## 5. 模型失败已清除旧结果，但报告完成标记仍有效

**根因**：`tool_river_init/hydro/pollution` 在计算前主动清除旧水质/水动力；路由 `_json` 在收到 error 后立即抛 `HTTPException`，跳过了后续 `invalidate_report` 与 `results_revision` 增量。

**修复**：
- 新增 `backend/model_state.py`：在调用前保存 `model_initialized`/`hydro_result`/`wq_result`/`geometry_revision` 的对象级快照；失败时只有在状态确实变化后才撤销报告并推进结果版本。
- `backend/routers/river.py` 的 init/hydro/pollution 与 `backend/agent/tools.py` 的河道工具共用该规则。
- 未发生状态变化（如参数校验在清除前失败）不误伤旧报告。

**回归**：`RiverModelStateSyncTests`。已有成功报告和 `results_revision=7` 时提交越界桩号：返回 400、旧 `wq_result` 被清除、`analysis_done=false`、状态 `stale`、版本推进到 8、旧摘要清空；初始化失败与 Agent 工具失败路径同样覆盖。

## 6. 河道页计算成功后未同步全局版本/报告状态

**根因**：`RiverView.vue` 三个模型动作只更新组件局部结果，不刷新 Pinia `status`；后端已撤销旧报告并推进 `results_revision`，前端仍持有旧版本。

**修复**：`runInit/runHydro/runPollution` 成功接纳结果后调用 `store.refreshStatus()`；保留原有工作区/请求版本/参数草稿保护，刷新失败只提示用户核对，不把已完成的模型结果标记为失败。

**回归**：`frontend/tests/riverRequestState.test.mjs` 新增 3 项，三个动作成功后均只刷新一次共享状态；原有迟到响应/参数编辑用例仍通过。

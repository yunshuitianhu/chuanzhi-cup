### 2.2 潮汐边界条件不生效 ✅ **实测** — ✅ **已修复（提交 `70491b6`）**

> **修复结果**：`bc_dn_dz` 的计算已移入 Newton 迭代循环内。
> 验收算例由 2 通过 / 4 失败 变为 **6 通过 / 0 失败**；
> 下游边界跟踪偏差 `1.1823 m → 0.0000 m`；Newton 迭代占用上限 `100% → 50%`；
> 恒定工况稳定性与质量守恒两项无回归。
>
> **但请务必同时阅读 2.7** —— 本修复只覆盖纯 Python 路径，
> 应用在本机的实际运行路径并未走到该求解器。

**证据**

```
# 改变潮汐振幅，观察下游边界节点 Z[-1] 的时间序列
振幅=0.0m   Z[-1] = [0.83   0.83   0.83   0.83   0.83  ]
振幅=0.8m   Z[-1] = [0.83   0.4466 0.4466 0.4466 0.4466]
振幅=3.0m   Z[-1] = [0.83   0.6302 0.6302 0.6302 0.6302]
```

**问题**：下游边界节点在第一个时间步之后**完全冻结**，不再随潮位过程线振荡。

与解析目标 `0.83 + 0.8·sin(2πt/12.42)` 对比：

```
    t(h)      Z[-1]实测         解析目标        偏差(m)
    0.50       0.4466       1.0302      -0.5836
    3.00       0.4466       1.6289      -1.1823
    6.00       0.4466       0.9148      -0.4682
最大绝对偏差: 1.1823 m  (潮振幅 0.8 m, 即 147.8% of 振幅)
```

**根因链（已验证）**

```
$ 拦截 _double_sweep 计数
30 步 × 上限 20 次 = 600
_double_sweep 实际调用次数: 600        ← 一次都没提前收敛
max|dZ| 全局最小值: 0.0067             ← 恰等于 bc_dn_dz
```

1. **`pure_py_hydro.py:377`** — `bc_dn_dz = bc_stage_target - Z[-1]` 在 Newton 循环**外**算一次
2. **`pure_py_hydro.py:232`** — 循环内 `dZ[-1] = bc_dn_dz`，是把该增量**直接赋值**给边界节点的修正量，而非设定目标值
3. 于是每次迭代都重复施加同一个陈旧增量 → 末节点每轮变化量恒为 `omega·|bc_dn_dz|`
4. **`pure_py_hydro.py:410`** — 收敛判据 `dz_max < tol`（tol=0.001）包含末节点，而 `|bc_dn_dz|≈0.0067 > 0.001`，**该条件永远无法成立**
5. 循环必然跑满 20 次并落入 **`:412` 的 `else` 分支**（未收敛处理）
6. **`:413-416`** 的注释声称"减小时间步长"，但 `dt_s` 在 `:366` 的循环中恒定，**没有任何自适应步长代码**；实际只做了一次粗暴回退（变化 >0.5m 就整体恢复）
7. 大修正（实测 `max|dZ|` 达 1.18）反复触发回退，水位场被反复重置 → 冻结

**附带确认的缺陷**（同一函数内，一并修）

- **`:112-113`** — `a_cont` 第一行算出的非线性项被第二行无条件覆盖，连续性方程实际退化为线性
- **`:96-99`** — `dB_j1` / `dK_j` / `dK_j1` 计算后**全文件无引用**（grep 确认），每次调用白做 4 组中心差分
- **`:246-247`** — 一段错误的回代循环，其结果在 `:256-274` 被完全覆盖。作者自己留了 `# Not quite right...` 注释。**这段必须删掉**——留着极易被后来者"顺手修正"从而引入真错误

**性能影响**：因每步跑满 20 次 Newton，计算量放大约 20 倍。实测 6h 模拟 20.4s、24h 模拟 81.9s。

**修改方案**：分两步，**先诊断后修改**。

- **第 1 步（诊断，不改代码）**：构造一个已知解析解的简单算例（如等宽棱柱河道、恒定流量、正弦潮位边界），确认修复后末节点能否跟踪解析解。这是修复的验收标准。
- **第 2 步**：修 `bc_dn_dz` 的传递语义——应改为在每次迭代**重新计算** `bc_stage_target - Z[-1]`，或在 `_double_sweep` 内改用目标值语义。
- 删除 `:246-247` 死循环、`:112` 死代码、`:96-99` 未用导数。
- 未收敛时的处理：至少 `warnings.warn` + 记录日志，不能静默返回。

**风险**：**高。这是数值求解器核心，改动可能显著改变输出。**

⚠️ **重要提醒**：修复边界后，模型中会出现真正的涨落潮流（当前因为边界失效，实测流量恒为正，`min Q = 6.9`）。届时 **2.3 的摩擦符号缺陷会被激活**。两处必须一起处理。

**验证**：修复前后必须对比——(a) 解析算例误差；(b) 真实样本的模拟结果变化幅度；(c) 反向流是否出现及其合理性。

### 2.3 摩擦坡降符号在反向流时错误 🔍 **源码确认，当前未触发**

**位置**：`pure_py_hydro.py:121-127`

```python
Sf = 0.0
if K_mid > 1e-6:
    Q_abs = abs(0.5 * (Q_j_n + Q_j1_n))
    Sf = Q_abs * 0.5 * (Q_j_n + Q_j1_n) / (K_mid * K_mid)   # 已是 |Q̄|·Q̄/K²，符号同流向
# Sf 符号: 与流向相同
```

**修改方案**：删除 `:126-127` 两行（`Sf` 已在 `:124` 带正确符号）。
**风险**：低（当前不触发）；但在 2.2 修复后需重新验证。

4. 该分支为**恒定流**模拟（SKILL② 关键约束 5 已记录"HEC-RAS COM 仅支持恒定流，非恒定流始终使用纯 Python"）
5. 结果：**用户点"运行河道模型"得到的是一张恒定流水面线，不是潮汐模拟**

**与 2.2 的关系**：2.2 修的是纯 Python 求解器，而这条路径在**本机根本不会被走到**。
两者都要处理，缺一不可——否则修好的求解器无人调用。

**连带影响**

- 验收算例、`test_smoke.py` 都**直接 import `pure_py_hydro`**，因此从不经过
  `detect_engine()`。**仓库里所有测试都没覆盖应用的真实运行路径。** 这本身是个测试盲区。
- `hecras_bridge.py:27` 写死绝对路径 `D:\my_HEC-RAS\Ras.exe`（见 3.3 X），
  而 `is_hecras_available()` 只用它选提示文案、不参与分支判断。

**资源泄漏（本轮实测复现）**：两次工具调用各留下一个完整 HEC-RAS 工程目录

```
%TEMP%/hecras_yayao_bi7q24og/   Yayao.prj  Yayao.g01  Yayao.u01  Yayao.p01  Yayao.r01  *.hdf
%TEMP%/hecras_yayao_owp0w8t9/
```

印证 3.3 Y 的判断：`hecras_bridge.py:307` 的 `tempfile.mkdtemp` 之后全库无 `rmtree`。
（本轮检查未发现残留 `Ras.exe` 进程，故 3.3 Z 的 `QuitRas` 异常路径问题仍属源码级风险，未实测触发。）

**修改方案**：需先决策，不急于动手。

- **方案 A（推荐）**：非恒定流一律强制走纯 Python 求解器，HEC-RAS 分支只在显式指定时启用。
  理由：SKILL② 自己就写明"非恒定流始终使用纯 Python Preissmann"，当前代码与自己的设计相矛盾。
- **方案 B**：保留 HEC-RAS 分支，但在 UI 与返回 JSON 中明确区分"恒定流模拟"与"潮汐模拟"，
  不让用户误以为看到了潮汐结果。
- 无论哪个方案，都要补：`hecras_bridge` 的临时目录清理、`dt_s < 60` 时入流文件非法的校验（3.3 C-39）。

**风险**：中。改变引擎选择会显著改变用户看到的结果——但这正是修复目的。
**验证**：改后调用 MCP 工具，`引擎` 字段应为纯 Python，`输出帧数` 应 > 1，`水位变幅` 应接近潮差。

## 1. 本次目标

用户反馈四个问题，要求一并解决：

1. 系统内模型不能直接看截图和视频帧，希望它可以随时读取系统内所需业务数据。
2. 回答充斥术语和内部状态。默认改用通俗语言，必要时用准确的比喻帮助理解。
3. 对话正文太小。顶部非对话内容默认收起，需要时展开。
4. “人工复核”等提醒过多。保留实际依据和关键限制，把一般性辅助分析说明集中在末尾。

预期体验：选第38帧并问“这里是什么情况”，系统实际向模型发送这张图；需要监测数据时按需读取对应记录。回答先讲看到了什么、与数据有什么关系，不先铺一页内部状态。聊天顶部只保留简短摘要和必要操作，正文占据主要空间。

本次包括消息组装、只读数据工具、前端交互、回答风格和验收，不能只改提示词或隐藏元素。

### 2.1 不是简单的“权限未开”

截至本次核对，[DeepSeek官方Vision文档](https://api-docs.deepseek.com/guides/vision/)说明 `deepseek-flash` 支持图片输入；Chat Completions 在 `user` 消息中使用 `image_url` 内容块。优先沿用当前模型接通图片，不必先换供应商。

执行时仍须在当前环境验证接口。官方能力声明、历史接口小样、产品端到端成功是三种不同证据。

给提示词加“你有看图权限”、把地址塞进普通文字、把本机路径发给模型，都不能替代真正的图片输入。远端模型也不能直接访问用户浏览器中的 `127.0.0.1` 地址。

本阶段完成静态图片和带时间戳的抽帧序列。未验证的原生视频输入，不得宣传为已经直接理解完整视频。

## 3. 系统业务数据的按需读取

### 3.1 访问范围

“随时访问系统数据”落实为用户提问时可读取本应用中的业务数据，而非后台不断上传全部数据。

| 类别 | 可读取内容 | 策略 |
| --- | --- | --- |
| 监测表 | 合法业务列、原始读数、时间、坐标、缺测/插值、质控记录 | 先摘要，再按时间、位置、指标、记录编号过滤并分页 |
| 筛查与地图 | 预警、聚类、点位、轨迹、选定范围 | 数值解释优先读取结构化数据 |
| 视频和图片 | 当前项目帧、用户上传/粘贴截图、已有视觉结果 | 按业务标识取图，保留时间和版本 |
| 河道模型 | 输入参数、已有正演/反演结果、配准、场景和状态 | 读现有结果不触发重算，未运行就说明尚无结果 |
| 外部资料 | 站点、候选排查资料、治理案例及已登记证据片段 | 保留来源和时间；新查询沿用既有工具 |
| 报告和任务 | 报告证据、研判卡片、排查任务及用户记录 | 只读查看，不顺便修改状态或覆盖报告 |
| 已保存项目 | 用户明确指定的其他项目中的业务数据 | 在现有会话可访问范围内只读加载快照，不切换或覆盖当前项目 |

每轮向模型给轻量目录、当前选择和可用工具。不要把整表、所有帧、全部报告每次塞进上下文。

这些工具不需要暴露 `.env`、密钥、凭据、Git内部文件或电脑其他私人目录。只接收业务ID与筛选条件，不接收任意路径、SQL、Shell命令或下载地址。

### 3.2 建议新增的三类只读工具

以下名称是建议，当前并不存在；可调整名称，但必须完成对应能力。

| 工具 | 输入 | 返回 |
| --- | --- | --- |
| `get_project_data_catalog` | 默认当前项目，跨项目需明确指定 | 数据是否存在、数量、字段、时间范围、版本、已有结果状态 |
| `read_project_data` | 数据类别、筛选、分页、预期版本 | 实际记录/统计、返回数量、总数量、截断状态、来源标识 |
| `inspect_visual_asset` | 附件ID或帧ID与版本，可选时间范围 | 实际图片引用、来源、时间、尺寸和发送/分析状态 |

实现约束：

1. 统计在服务器计算。20条示例不能冒充全时段统计；返回 `returned_count`、`total_count`、`truncated`，支持继续读取。
2. 复用 `question_context.py`、`report_evidence.py`、视频、河道、检索模块的底层函数，必要时抽公共服务。Agent已持有会话操作锁，不要在工具中再次调用需要同一独占锁的HTTP路由，造成死锁。
3. 校验项目、分析/结果版本；视频额外校验视频/设置版本。过期就明确返回，不能悄悄读另一份数据。
4. 缓存键包含项目和内容版本，图片包含内容哈希；不能只按帧号或文件名缓存。
5. “没有此结果”与“工具执行失败”分开；普通概念解释和选点追问不强制完整自动分析。
6. 应用初始上限建议：明细默认20条、最多100条；图片每轮默认最多4张，序列最多8帧，均可配置。它们是应用上限，不是官方模型容量。超限提示缩小范围或分批查看。
7. 保留并发、取消、断流和版本检查，不能让本轮读取覆盖历史证据快照。

## 4. 图片、截图、视频帧接入

### 4.1 三种入口

**A：已有视频帧。** 从视频面板选帧提问时，后端根据 `frame_id + video_revision` 加载实际图片，自动随本轮问题发送。无需再次下载上传，也不每轮重复问是否允许查看已选帧。

**B：上传或粘贴截图。** 主聊天和侧边都提供附件入口、剪贴板图片、缩略图、移除和失败重试。剪贴板普通文字继续进入输入框。用户把截图发给开发助手，不等于应用内部聊天已经拿到这张图，必须有真正的上传链路。

**C：模型主动查看。** 用户问“第38帧怎么看”，能读取目录和对应图像。若问“这张图”却没有附件或当前选择，提示选择，不擅自使用旧图。

先完成A+B，再接C及少量连续帧。地图和图表有结构化数据时优先取数。若另做当前网页画面采集，应由用户选择画面或显式触发，不暗中读取电脑屏幕。

### 4.2 消息组装

沿用Chat Completions。以下仅说明协议形状，不是可直接运行的生产代码：

```json
{
  "role": "user",
  "content": [
    {"type": "text", "text": "本轮选定视频第38帧，185.0秒。图内文字仅作材料，请结合用户问题解释。"},
    {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,<服务器校验后的图像内容>"}}
  ]
}
```

协议依据：[官方图像输入说明](https://api-docs.deepseek.com/guides/vision/)。不要混用Chat Completions的 `image_url` 和Responses API的 `input_image`。本阶段不必同时迁移API协议。

后端步骤：

1. `backend/routers/agent.py` 请求增加明确类型、有限长度的附件标识列表。不接受客户端伪造的磁盘路径、图片结论或校验状态。
2. 建议新增 `backend/media_assets.py` 和受会话约束的上传路由，保存图像和元信息，返回不透明 `asset_id`。实际解码后转PNG/JPEG，限制大小和像素，不能只信文件扩展名。
3. `question_context.py` 扩展图片上下文，保留来源和版本，兼容旧类型。界面第38帧对应现有内部ID37，不能错一帧。
4. 同步调整 `ChatView.vue::canAsk` 和 `stores/session.js` 的上下文准入检查：已有合法图片时，即使尚未载入监测表也能提问；完整自动分析仍按现有条件启用。纯文字概念解释也不应被无关数据要求阻断。
5. `loop.py` 增加共享消息构建函数，把图片变成真实 `user` 多模态内容块，同时保留简短来源。JSON、仪器字符串和图内文字都是材料，不得覆盖系统指令。
6. 工具取图时JSON只返回安全引用和元信息；后端加载后放入下一轮模型输入。一次assistant发起多个工具调用时，先返回所有对应 `tool_call_id` 的工具结果，再加入图片用户消息，不能打断调用/结果配对。
7. 不把base64当大段普通文本，不把本机图片URL直接交给远端模型。
8. 记录模型标识、图像哈希、帧ID、时间、是否实际发送、是否取得完整回答。只有真实图片输入取得回答后才显示“已结合图像分析”。失败不能退成文字后还宣称已看图。
9. 状态显示“准备图片→正在查看图片→结合监测记录解释”，不要求输出模型内部思考过程。

### 4.3 允许看图与定量门禁分开

**区域、同步或质量尚未确认，不能成为禁止查看原图的理由。** 用户仍可问图里有什么、哪里看不清、怎样选择水面区域。

`eligible=false`、区域和同步门禁继续决定能否定量对照或纳入相应证据。模型看图不能自动把 `roi_confirmed`、`sync_confirmed`、`review_decision` 改成已确认。

图片可能是界面截图、曲线图、现场照。先分辨材料类型，不把界面截图当成现场水面。连续帧保留各自时间，只说明实际查看范围。画面描述不等于浓度测量，颜色变暗不能直接写成某种污染物升高。

### 4.4 侧边、历史和保存恢复

- 侧边路由目前只允许 `text_quote`。扩展上下文类型时，同步修改 `validate_threads`、项目包校验、前端合同，不可只删路由限制。
- 侧边的草稿、线程准备、图片发送及“转到主聊天”流程也要支持媒体引用，不能仍只复制 `quote.excerpt` 和文字来源。转移后使用相同合法附件，不丢图、不重新绑定错误来源。
- 共享图像加载、表达规则和只读数据能力。侧边若加工具循环，只给只读白名单，不生成正式报告、不改任务或主聊天状态。新读取资料进入侧边自己的来源目录。
- SSE、普通历史、日志不输出图片base64、请求头和密钥；聊天保存文字和附件引用，图像独立保存，每轮按需加载。
- 新附件必须随项目保存、导出、导入、恢复。使用有大小上限及哈希校验的媒体条目或等效方案，更新 `project_codec.py` 与项目仓库逻辑；不能只存浏览器临时URL。旧项目缺少新字段时使用兼容默认值。
- 现有项目包已保存视频帧，不要求删改这些历史数据；避免每轮把图片内容重复写入 `full_messages` 使体积不断翻倍。
- 项目切换、视频替换、附件移除后取消不适用的待发送请求；历史来源不能重绑当前新图。
- 移除输入区引用与删除已保存媒体分开，不能移除一个缩略图就损坏历史回答。

## 5. 把回答改成用户能读懂的语言

### 5.1 默认回答顺序

1. **先说结果：** 1—3句话直接回应，优先解释用户选定对象。
2. **再给依据：** 通常挑2—4项真正有用的数据/画面现象，保留时间、单位和引用入口。
3. **必要时解释概念：** 术语首次出现用一句话说明，可用短比喻，之后回到实际数据。
4. **下一步建议：** 只给与问题相关的1—3项操作。普通定义不强制附整套排查计划。
5. **最后说明定位：** 水质研判、来源分析末尾集中放一条辅助分析说明。

普通追问建议150—350字，复杂解释可300—600字；完整报告按实际需要组织，不强制每次长报告。长度是软目标，不得为了短而漏掉关键异常或用户要求的专业细节。

### 5.2 共享表达规范

建议新增 `backend/agent/response_style.py` 或等效公共模块，自动分析、自由聊天、侧边和报告共同引用。以下可作为风格提示：

> 面向希望理解河道情况的普通用户。先回答问题，再用少量实际依据解释。默认短句和日常语言，必要术语首次出现时简要说明，不把工具字段清单当答案。可以使用准确比喻，但不能用比喻代替证据、编造因果或改变数值含义。一般性的辅助分析说明在末尾集中一次表达；影响本题答案的具体问题在相关处简短说明。用户要求专业细节时提供参数、原始字段和完整依据，不输出内部思考过程。

`EVIDENCE_RULES` 中数值、来源、引文、仿真身份和因果判断规则仍有效。把事实边界与表达方式分层，不能为了通俗而绕过事实校验，也不要把所有内部检查项目逐项复述给用户。

### 5.3 建议语言映射

| 内部术语/字段 | 默认用户解释 | 详情保留 |
| --- | --- | --- |
| `roi`、`roi_confirmed=false` | 还没有选定要分析的水面区域，这些特征目前来自整张画面 | 区域坐标和状态 |
| `sync_confirmed=false` | 视频时间还没与仪器记录对齐，暂时无法判断是否对应同一时刻 | 时间偏移和窗口 |
| Laplacian方差 | 画面细节指标，偏低可能是模糊，也可能只是水面平静 | 指标、数值和计算说明 |
| 溶解氧 / DO | 水里可供生物利用的氧，可以理解成水体的“氧气储备” | mg/L、阈值依据 |
| 正演 | 给定排放设定，计算污染物接下来怎样移动和变化 | 方程、边界和参数 |
| 反演 | 根据浓度变化倒推哪些排放设定更符合数据，类似根据脚印推测来路 | 参数可辨识性、误差和候选解 |
| `not_configured` | 尚未设置，并说明缺少哪项设置 | 原始状态码 |
| `records_truncated=true` | 统计覆盖所选全部记录，下方只展示一部分 | 返回量、总量、分页 |
| 质控突刺/恒值 | 这段读数突然跳高 / 连续重复，值得重点查看 | 规则、阈值和原始记录 |

不要强制每段修辞。“脚印”不意味着找到唯一来路，“氧气储备不足”不意味着证明某企业排污。不要把相关性比喻成已经成立的因果关系。

### 5.4 结合用户截图的改写示例

以下只示范表达。数值取自用户提供的界面截图，不是本次新运行结果；实施时必须重新读取当时项目数据。

**问题：这段氨氮数据说明什么？**

推荐：

> 这次走航里，氨氮的平均读数与最高值相差很大。表中平均值约6.67 mg/L，最高记录560.15 mg/L，建议先定位高值出现的地点和前后记录，看看它是持续的一段，还是短暂跳高。
>
> 你现在看到的20条示例只是全程1805条记录的一小部分。开头这小段比较平稳，不能代表整段河道都平稳。无人船同时在移动，这些变化也不能直接当成固定地点随时间恶化。
>
> 可以先在地图上打开高值点，再查看它前后的读数和视频。
>
> 本系统提供辅助分析，具体成因仍需结合现场情况确认。

避免先列 `position`、`raw_preserved`、`interpolated` 等字段，让用户自己猜含义。也不能把这份未独立核验数据直接写成现场确定事实。

**问题：第38帧是什么情况？**

- 图像真实发送成功：先说画面可见内容，再回答用户所问现象，需要时读取关联监测记录。没有看到实际图像前，不能预写“发现排口”“看到漂浮物”等结论。
- 图像获取/发送失败：“这次图片没有读取成功，我目前只能看到第38帧的记录信息。你可以重试读取图片。”并提供重试。
- 区域未指定：一句话说明“目前按整张画面解释，若要比较水面特征，可以先框选水面区域”。不把所有 `false`、`pending` 铺满正文。

### 5.5 技术细节按需查看，原文保持一致

- 来源、视频参数、质控详情通过受控Vue折叠区提供，默认通俗摘要，需要时查看原字段。
- 不让模型输出未受支持的HTML折叠标签绕过 `SafeMarkdown`；交互由组件承载。
- 不用正则在生成后批量删句、替换字段或改写引文，否则流式显示、选文字、引用偏移和保存内容可能不一致。
- 通俗表达在提示词和服务端展示模板里完成；直接引文仍按原文展示，不能改成“通俗引文”。
- 数值、单位和证据可核对。不能把缺测补成0、仿真改称实测或权重改称概率。

## 7. 减少重复的“人工复核”措辞

### 7.1 用户展示规则

1. 普通回答不默认以长篇身份声明开头。数据身份用短标签或来源详情，先回答问题。
2. 研判类回答末尾统一一次：“本系统提供辅助分析，具体成因仍需结合现场情况确认。”
3. 只解释术语、按钮、界面错误时，不机械添加污染责任提醒。完整来源分析或报告才需要相应定位说明。
4. 真正影响本题的条件就地简述，如“视频与仪器时间尚未对齐”，不再追加多段同义声明。
5. 默认界面中的“人工复核”入口按真实动作改为“检查记录”“确认设置”“待确认”等；不能全局统一替换成同一个词，更不能改成已确认。
6. “仿真数据”“历史结果”“图片未读取”“任务失败”等影响理解的信息仍须清楚显示，它们不是要删掉的套话。

### 7.2 后端、报告同步调整

- 不全仓库替换或删除“人工复核”。机器字段、操作记录、证据校验、质量规则和门禁含义继续保留。
- 主聊天、自动分析、侧边和报告统一规则。只改一个提示词不能解决报告抬头和其他路径的重复。
- `report.py` 的确定事实仍由服务器建立；详细元信息移入数据与依据详情或导出附录，正文先给摘要。
- 通用定位语可由渲染层或报告模板统一添加一次，并确保复制/导出一致；生成提示要求避免重复。历史正文不做后台批量重写。
- JSON快照、完整依据和专业详情保留原字段与必要说明。减少重复展示不等于删除审计记录。
- 区域、同步、质量等只在相关问题里说明实际影响，不因为系统有这些字段，就每次输出完整状态表。

## 9. 验收标准

### 9.1 功能与真实模型

| 场景 | 操作 | 应有结果 |
| --- | --- | --- |
| 指定帧 | 选第38帧问画面内容 | 加载内部ID37，实际请求含图片，答复不只复述特征 |
| 未确认区域 | 不改区域设置直接看图 | 可以看原图，但不自动确认区域、不绕过定量门禁 |
| 粘贴截图 | 在主聊天粘贴可辨文字测试图 | 缩略图、真实传图，能结合图中文字解释 |
| 侧边追问 | 对同一图片在侧边继续问，并转到主聊天 | 相同来源和附件，不写主报告、不改任务、不丢图 |
| 只有截图 | 新会话不上传Excel，仅粘贴截图提问 | 可以发送并解释图片；不假造监测数据，完整自动分析仍受数据前提约束 |
| 连续帧 | 选择少量有明确变化的测试帧 | 区分时刻，只说明实际查看范围 |
| 纯文字 | 无图问术语 | 正常流式输出，不要求无关上传或完整自动分析 |
| 关联取数 | 问185秒附近仪器值 | 按已配置同步条件读取；未对齐则说明无法对应，不擅自默认同步 |
| 模型数据 | 问本次模拟边界与结果 | 读现有结果，不偷偷重跑，不把设定源当反演结果 |
| 全量/示例 | 问整段趋势，打开前20条 | 全量统计和示例分开，不用示例冒充全量，也不长篇解释分页机制 |
| 数据切换 | 发图前切项目或替换视频 | 拒绝过期引用、保留问题，不串项目图片 |
| 故障 | 无法解码、超限、超时、模型拒图 | 显示实际原因、可行操作，保留草稿与重试，不假称已看图 |
| 恢复 | 保存、重启、导出再导入独立测试项目 | 附件可恢复，原用户项目不被覆盖 |

真实模型至少测：一张答案可确认的程序生成图、一张界面截图、一张已授权的项目视频帧、一个少量连续帧场景。记录图片输入、服务返回模型标识、完成状态和可核对答案。HTTP 200不等于看图正确，mock不等于产品端到端成功。

用户样本在独立测试副本中使用。不要把原始私人图片、视频、完整私人报告或含密钥请求提交Git；验收保留摘要、哈希和必要的脱敏截图。

### 9.2 回答质量

固定问题集覆盖主聊天、侧边、自动分析和报告：

1. 这张图说明什么？
2. 这段氨氮为什么突然高了？
3. 什么是溶解氧，低了会怎样？
4. 第38帧有哪些问题？
5. 正演和反演有什么区别？
6. 能确认污染从哪里来吗？
7. 没有视频能分析吗？
8. 请只给我专业参数和原始字段。
9. 这份数据里哪些结论是仿真的？
10. 这个错误提示是什么意思？

逐项检查：开头是否回应问题，必要术语是否解释，比喻是否准确，是否堆无关状态，数值/单位/引用是否正确，提醒是否重复，要求专业细节时是否完整。

采用样例对照和实际阅读检查，不能用“出现人工复核就判失败”的禁词正则。真实动作名称、直接引文和历史记录保留原貌。

### 9.3 自动化与回归

新增测试要验证行为，而非仅检查某段提示词存在：

- 模型消息确有图像块，图像与所选帧一致，工具调用结果顺序合法。
- 质量门禁不阻断看图，却仍限制定量对照；模型不能改确认状态。
- 分页、全量统计、过期版本、跨项目隔离、图片格式/大小和内容哈希。
- 新媒体保存恢复、旧包兼容、侧边类型和引用检查。
- 取消、断流、重试不重复写报告，失败仍按逻辑操作及版本追踪。
- 顶部默认收起、展开后草稿和引用保持、状态可见、键盘焦点及矮屏滚动。
- 选文引用、原文、流式暂停、复制和导出不因语言优化失真。

在项目已配置依赖环境，从仓库根目录运行既有门禁：

```text
python scripts/check_ci.py
python scripts/export_frontend_contracts.py
npm --prefix frontend run check
```

若解释器、Node或依赖不在PATH中，先定位项目当前运行环境，不为通过检查擅自升级整个依赖栈。这些命令不包括真实模型与浏览器验收，后两者单独记录。

上一轮报告可靠性修复必须保持：同名不同参数的工具不能互相抵消失败；报告前综合摘要刷新有效；历史裁剪不能假定成功；部分失败不能显示整体完成。

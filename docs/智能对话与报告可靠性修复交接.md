## 2. 已核实事实：不要把历史失败与最终结果混为一谈

### 2.1 当前页面可复现的问题

展开当前进度历史，能看到：15轮、19次工具调用，其中18次成功、1次失败。与报告相关的真实顺序为：

```text
读取监测摘要 → 筛查异常点 → 分析视频 → 视频交叉印证 → 整理综合证据
→ 地理/周边/卫星/国控查询 → 检索治理案例（48.2秒）
→ 生成分析报告：失败（0.0秒，前置步骤/参数类提示）
→ 再读监测摘要 → 再次筛查异常点 → 再整理综合证据
→ 生成分析报告：成功（11.8秒）
→ 读取卡片目录 → 提交分析卡片
```

因此：**当前可见的报告工具第一次失败，随后重试成功；不能说整轮始终没有生成报告，也不能把第一次失败删除或改成成功。**

服务日志中有“报告正文生成完成，finish_reason=stop”，与上述后一次成功相符。早期对话中存在“知识库依赖不可用”的历史记录；当前这一轮治理资料检索显示成功，不能把早期失败直接解释成当前依赖仍不可用。

当前标题显示“本轮已完成”，又显示“失败1”和“不能代表整轮完成”的说明。现有实现没有表达“曾失败但已恢复”，用户无法快速判断最终到底完成了什么。

### 2.2 布局缺陷已经定位

`frontend/src/views/ChatView.vue`：`AgentProgress`位于`.conversation`之前，处于固定高度聊天工作区的正文外部。末尾样式为工作区建立flex布局，但进度面板会持续占用可用高度，压缩正文滚动区域。

`frontend/src/components/AgentProgress.vue`：

```js
const failureSteps = computed(() => steps.value.filter(step =>
  ['failed','partial','cancelled','skipped'].includes(step?.status) || !!step?.notice))
const historySteps = computed(() => historyOpen.value ? steps.value : failureSteps.value)
```

“收起历史”并未收起整个面板；所有带notice的成功步骤和历史失败仍在正文上方列出，同时还有标题、统计、说明和最新步骤。不要只把列表最大高度调小，必须调整信息层级与布局。

### 2.3 报告前置依赖失效：代码路径与隔离验证

已确认的代码路径：

```text
Session.set_station_result(...)
  → invalidate_report()
  → 清除 get_comprehensive_summary / generate_final_report 完成标记
  → 若未重新取得综合摘要，generate_final_report 前置校验拒绝生成
```

`backend/session.py`的`invalidate_report()`会撤销旧摘要/旧报告标记，这是必要的版本保护。当前Agent先取得综合摘要，后查询国控数据，存在让刚完成摘要失效的调度路径。

本次使用独立Session与4条受控记录验证：基础步骤成功后更新站点结果，`get_comprehensive_summary`标记确实消失；随后报告调用被拒绝；重新获取综合摘要后报告调用可以通过。报告生成器使用替身，未调用在线模型，也没有操作用户当前Session。

另外，只读检查了项目`111`已保存的v10快照，其历史工具上下文同样包含“报告前置条件不满足→后次成功”的记录。**该快照状态是stale，不能冒称它就是当前106秒任务的原始调用追踪。**

结论边界：依赖失效路径已复现，且与当前工具顺序高度一致；当前实时任务首个错误的完整结构化结果仍需接手者获取后逐条核实。不能排除单次调用的缺参或类型错误。现有`generate_final_report`schema要求字符串`summary`，但实现实际从会话重建证据，这也是需要审查的接口冗余，不能未经核对就断言它是此次根因。

## 4. P0-A：将进度区改为紧凑摘要与可展开详情

建议方案：

1. 运行中显示一条紧凑状态：实际当前阶段、耗时、停止入口、查看步骤。默认不铺开完整工具历史。
2. 任务终止后自动压缩为一行或两行，如“分析完成 · 报告已生成 · 1次失败已恢复 · 查看19次调用”。这是目标示例，文字必须依据实际状态生成。
3. 完整步骤和异常说明进入折叠区或独立抽屉；用户点击“查看详情”才展开。成功但带说明的步骤不应强制常驻正文上方。
4. 未恢复的错误在紧凑条保留数量与入口，避免用户遗漏；不默认展开长列表。打开详情后能清楚定位失败原因。
5. 详情区有独立可控滚动、关闭按钮、正确焦点管理；如果采用模态抽屉，需要Escape、焦点限制与关闭后返回焦点。
6. 使用统一flex/grid剩余高度分配，让正文滚动区获得主要空间。检查现有两组`.stream`/`.has-progress`高度规则与末尾覆盖规则，消除互相冲突的魔法常量；不要简单叠加第三组覆盖样式。
7. 输入框与发送/停止可访问，正文长内容能滚动到底；用户上翻、选字时不强制跳到底部。全局划词菜单必须仍可用于状态说明以外的普通正文和表格。

建议验收预算（属于本次目标，不是已达到指标）：在1280×800桌面视口、侧栏关闭时，终止任务的折叠摘要区不超过约80px，正文可读区域至少约320px；390×844移动视口内摘要不超过约120px，正文至少约240px。极小窗口允许外层滚动，但不能遮住输入控件。详情展开不能造成正文不可访问。

## 5. P0-B：修复“先摘要、后改证据、再报告”的依赖链

### 5.1 保留必要校验，修复调度而非绕过校验

- 不删除`invalidate_report()`，不强行填充`analysis_steps`成功，不使用旧摘要绕过报告前置检查。
- 自动分析应先完成会改变证据上下文的采样检测、视频交叉印证、站点/模型等所需查询，再生成对应版本的综合摘要与报告。
- 仅修改提示词不能保证成功。报告调用前由后端显式核对所需步骤和证据版本；发现“摘要因外部结果更新而失效”时，执行最小必要刷新，通常是更新综合摘要，而不是把所有检测重跑一遍。
- 不无条件重复`find_black_spots`：它会通过`set_detection()`撤销部分周边线索和资料步骤，可能进一步造成不必要的失效循环。
- 报告、前置步骤、分析卡片必须绑定同一项目、数据/配置及相关结果版本；版本变化时重新构建或明确拒绝，不能继承上轮完成标记。
- 修复`generate_final_report`的参数契约：评估将无实际用途的`summary`改为可选/移除，并处理已有调用兼容；如果保留，须在schema、调用说明和测试中一致。报告事实继续从服务端会话取证，不能信任模型传入的数字。
- 对明确可恢复问题允许有限次数恢复；为同一依赖状态设置重试上限，防止重试风暴。达到上限说明缺口，不改成假成功。
- 到达`MAX_TURNS=15`时不能以最终聊天文字替代未完成的正式报告。应合理预留报告与卡片预算；仅提高轮次上限不是修复。

### 5.2 防止已生成报告被后续自由回答遮蔽

现在的报告工具返回报告正文，之后Agent仍可能继续生成一段最终回答。接手者需核对：用户能否直接阅读、定位到真正生成的报告，是否只看到了“已提交5张卡片”。建议把已生成报告作为明确的本轮产物呈现，聊天总结链接/定位到该产物。不要让“卡片提交成功”冒充“报告生成成功”，也不要产生两份版本不明的报告。

## 6. P0-C：建立尝试记录与最终有效状态的双层语义

保留每次调用原始状态；另计算每项业务能力的最终有效结果。

推荐增加或等价表达以下概念：`attempt_id`、逻辑操作/阶段标识、输入证据版本、`retry_of`/`recovered_by`、结构化错误码、产物标识。具体schema由实施者与现有协议协调，**这些字段目前不是已存在功能**。

- 同名工具不一定是重试：不同坐标、关键词、项目、数据或结果版本不得只凭工具名合并。
- 报告首次失败，后续对当前有效版本成功：摘要显示“报告重试后完成”，详情保留两次调用及其关系。
- 报告仍失败：整体不能显示无保留的“本轮已完成”；允许展示可复核的部分正文，明确“报告尚未生成”。
- 可选源因无视频/缺外部数据而跳过：显示“不适用/未取得数据”，不要伪造成功，也不要把正常缺项说成系统崩溃。
- 国控请求成功但关键词零匹配，与离线降级、网络失败是不同状态。当前进度中的早一次背景查询提示不能盖过后一次查询结果，也不能把非同期站点值用于历史走航因果认定。
- 普通聊天、自动分析、断线恢复、停止和刷新后的状态一致。后端返回最终有效状态，前端不根据文本猜测“已恢复”。

重点审查`loop.py`目前按工具名覆盖`session.analysis_steps[name]`，但`AgentRun.steps`保留每次尝试的双重行为。当前计数18成功+1失败是尝试级事实；不能当作最终有1项尚未恢复，也不能把19次尝试误称为19种独立任务。

## 7. P1：错误边界、恢复与流式体验

### 7.1 错误要可执行

现有`tool_notice()`通过关键词把大量错误映射为“输入、参数或前置步骤不满足要求”。改为明确区分：

| 情况 | 用户应看到的含义/操作 |
| --- | --- |
| 摘要版本失效 | “站点结果已更新，正在刷新综合摘要后生成报告”；仅在真实自动刷新时显示“正在” |
| 真正缺少必填参数 | 显示缺少的安全字段名，并由Agent修正调用；不让用户猜配置 |
| 无监测表 | 引导载入监测表，不执行报告生成 |
| 未上传视频 | 视频相关步骤不适用，监测表分析继续 |
| RAG缺依赖/索引/模型 | 明确具体类别和检索状态；允许生成不含案例的报告并说明缺口 |
| 外部鉴权/超时 | 可检查配置/稍后重试，限制次数；已完成结果保留 |
| 报告输出为空/被截断/非法引用 | 不标为完整报告；保留失败原因和可恢复入口 |

前端只显示经过白名单处理的说明；完整诊断留在脱敏日志或受控详情。不得把Key、Token、绝对私密路径或模型内部思考链输出给用户。通过真实阶段与工具事件展示“思考状态”，不伪造推理内容。

### 7.2 输出与长任务

- 48.2秒的首次资料检索与本地嵌入模型冷启动同时出现，日志支持冷加载确实发生；各部分准确耗时仍需测量，不能把全部时间都归为网络故障。
- 为实际检索/模型加载和报告生成提供准确阶段，不添加假进度百分比。UI不因等待扩大空白状态块。
- `report.py`当前是内部非流式报告调用。可先保持该接口并显示真实阶段；如改流式，必须同时处理停止、断线、最终完整性、引用校验和产物提交，不能把未完成内容保存为成功报告。
- 最终聊天SSE正文继续分批渲染；检查chunk含中文、Markdown代码块/表格时的布局稳定性。停止、返回最新、文本选择、侧边问答不互相抢焦点或反复重排。
- 不为展示新增自动重复收费请求。真实在线验收使用隔离测试项目，注明次数与结果；报告失败时给用户显式重试入口。

## 9. 必须补充的回归用例

1. 先成功取得综合摘要，再更新站点结果：旧摘要失效；报告协调器正确刷新后再生成，不需要重跑全部检测，最终报告使用新版本。
2. 报告失败后同版本重试成功：尝试记录一失败一成功；最终业务状态“已恢复”；收起时不铺开失败正文。
3. 同名工具不同查询条件/版本：不误标为一次重试；较旧的成功不能恢复较新的失败。
4. 当前版本报告仍失败、缺少必要步骤、无正文、输出截断或非法引用：保持未完成状态，不能靠卡片或最终聊天收口判成功。
5. 有视频、无视频、正常无黑点、仿真跳过真实企业归因：可适用步骤正确；不杜撰视频/污染源。
6. RAG缺依赖、离线站点、站点空结果、401/403、超时：结果分类清楚，各源独立降级。
7. 桌面与移动浏览器：长报告、19次以上调用、若干失败说明，详情默认收起；正文和输入控件可用。
8. 用户手动展开详情后继续流式输出：展开意图不被每个事件覆盖；关闭后回到合理焦点。
9. 上翻、选字、主/侧边草稿、项目切换、停止、SSE断线和迟到事件：不丢草稿、不串项目、不错误标记完成。
10. 真实在线全流程：在隔离项目用原始样本和至少一份无视频仿真验证；保存最终状态、调用顺序、产物、失败/恢复记录及截图，不声称模拟测试证明真实检测准确率。

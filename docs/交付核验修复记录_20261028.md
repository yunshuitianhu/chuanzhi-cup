## 2. R01：失败后内存、绑定与重启恢复一致

### 2.1 根因

旧流程在 `repository().write(blank, ..., new=True)` 中直接写入 `bindings`，之后才读取快照并调用 `apply_snapshot`。写入成功但后续读取或物化失败时：

- 当前内存仍是旧项目（`apply_snapshot` 在物化完成前不改会话字段）；
- 数据库 `bindings` 已指向新项目；
- 服务重启或新 `SessionStore` 恢复同一会话时，会打开未成功展示的新项目。

原项目仍在数据库中，不是删除，但用户会遇到“失败后换项目”的错位。

### 2.2 修复

`backend/projects.py`：

- `write(..., bind_session=False)`：只创建项目和修订，不写当前会话绑定；默认值保持原行为。
- `prepare_snapshot(snapshot)` / `publish_snapshot(...)`：从 `apply_snapshot` 拆出。所有可能失败的磁盘 I/O（运行目录、附件物化）在 `prepare_snapshot` 完成；`publish_snapshot` 只改内存。
- `activate(session, info, snapshot)`：`prepare` → 记录旧绑定 → 写入新绑定 → `publish`。`publish` 失败时把绑定恢复为旧值；绑定写入自身失败时不改内存。
- `activate_new(session, info)`：回读刚写入的新项目并 `activate`；失败时调用 `discard_candidate`。
- `discard_candidate(project_id)`：仅删除 `revision==1` 且 `bindings` 无引用的本次候选，连同其快照文件；不触碰旧项目、用户快照和历史版本。

调用方统一为同一发布顺序：

```text
保存当前项目
→ write(新项目, bind_session=False)
→ activate_new：read 回读 → prepare 物化 → bind 绑定 → publish 内存
→ 失败：恢复旧绑定 + 仅清理本次未绑定候选
```

覆盖位置：`POST /api/data/samples/{id}/load`、`POST /api/projects`（`from_current=false`）、`POST /api/projects/import`、`POST /api/projects/{id}/open`。`POST /api/projects` 的“从当前另存”仍由一次 `write(new=True)` 完成，项目插入与绑定在同一数据库事务内，没有“写入成功、应用失败”的中间态。

### 2.3 新增回归

`tests/test_sample_catalog_regressions.py`：

- 旧项目 S01 成功后，载入 S02 时快照回读失败：503、内存 S01、绑定 S01、新 `SessionStore` 恢复 S01、项目数仍为 1。
- 写入后、附件物化失败：同上。
- 绑定成功、内存发布失败：绑定回滚到 S01，恢复仍为 S01。
- 绑定写入失败：旧内存和旧绑定不变。
- 正常载入、S01 零预警、S06 检测、保存后重开、检测失败不回滚等原有语义继续通过。

`tests/test_projects_regressions.py`：

- 空项目创建与导入在发布阶段失败：503，旧项目内存/绑定/恢复目标不变，候选项目被清理。
- 打开其它项目在发布阶段失败：绑定回滚到原项目。
- `discard_candidate` 对已绑定项目返回 `False`，只删除未绑定的新建候选。

### 2.4 限制

- 故障由 `unittest.mock` 注入（回读 `OSError`、物化 `OSError`、发布 `OSError`、SQLite 绑定失败），不是真实磁盘损坏或权限故障。
- 如果“内存发布失败”和“恢复旧绑定”同时失败（持续性数据库故障），代码会记录警告，但无法保证数据库绑定与内存一致；该双重故障未在真实现场复现，属于残余风险。
- 发布失败时，候选项目的内存状态未被修改，是因为 `publish_snapshot` 只做字段赋值；如果未来在该函数中加入可失败的 I/O，需要重新评估这一前提。

## 3. R02：示例资源读取进入 503 错误边界

### 3.1 根因

`_validate_sample` 中的 `path.read_bytes()` 没有捕获 `OSError`。`load_manifest` 会先读取并校验每份 CSV，因此只要任一 CSV 不可读：

- `GET /api/data/samples` 和载入接口都返回未分类的 500；
- 前端看不到可操作的中文说明；
- 读取大小没有上限，完全信任 manifest 声明值。

### 3.2 修复

`backend/sample_catalog.py`：

- `_read_bounded(path, limit, label)`：最多读取 `limit + 1` 字节；`OSError`/`PermissionError`/`FileNotFoundError` 统一转成 `SampleResourceError`，文案为“无法读取；请检查 data/samples 资源或目录权限”，不含绝对路径。
- `_require_regular_file`：统一检查普通文件、符号链接和路径逃逸。
- `_validate_sample`：先校验声明大小和哈希格式；用 `stat()` 获取实际大小，实际超过 `MAX_SAMPLE_BYTES` 时直接拒绝；实际大小与声明不一致时拒绝；再用有界读取复核长度和 SHA-256。
- `load_manifest`：清单也走有界读取（上限 2MB），超过上限或 JSON 损坏返回资源错误。
- `get_sample`：重新检查路径包含关系，按声明大小有界读取，并在返回前复核哈希；调用方解析的就是校验通过的同一份字节。

### 3.3 新增回归

`tests/test_sample_resource_regressions.py`：

- 仅对 S01 CSV 注入 `PermissionError`：目录和载入接口均返回 503，正文含“无法读取”和相对路径 `data/samples`，不含绝对样本路径；旧数据、文件名和分析版本不变。
- 文件通过存在性检查后注入 `FileNotFoundError`：返回 503 资源错误。
- 实际文件 65 字节、清单声明 10 字节、上限临时降为 64：在完整读取前以“实际文件超过大小上限”拒绝，响应不含临时目录路径。
- `get_sample` 返回的字节长度和 SHA-256 与清单一致。

### 3.4 限制

- 权限错误和文件消失由受控故障注入模拟；未在真实 ACL 或磁盘损坏环境复现。
- 目录接口仍会校验清单内所有示例文件；任一份损坏时整个目录返回 503，这是既有的“不静默返回空列表”设计，未改为单例容错。

## 4. R03：打包器拒绝未跟踪文件

### 4.1 根因

`scripts/package_delivery.py` 只运行 `git diff --name-only HEAD` 和 `git archive HEAD`：

- `git diff HEAD` 不枚举未跟踪文件；
- `git archive` 只打包已提交文件；
- 结果是“新建但尚未 `git add` 的功能文件”会被静默漏出交付包，与交付说明的承诺不一致。

### 4.2 修复

- 新增 `worktree_problems(changed, untracked)`：未提交源码和未跟踪文件分别给出明确错误；`work/`、`data/projects/`、`.rag_index/`、`仿真数据/` 等 `RUNTIME_PREFIXES` 按既有运行目录策略排除。
- `main()` 增加 `git ls-files --others --exclude-standard -z`，与 `git diff HEAD` 一起传入门禁；有阻塞项时 `parser.error` 退出 2，不生成 ZIP。
- `.gitignore` 增加 `AGENTS.md`（旧版指令副本，已由 `CLAUDE.md` 取代）和 `仿真数据/`（原始 Excel 用户资料），避免本地资料误入库或误触发门禁。
- 同步修正 `docs/交付说明_20261028.md` 与 `docs/交付包与隔离迁移验收.md` 的打包说明。

### 4.3 验收

- `tests/test_delivery_regressions.py` 覆盖：未提交源码被拒、未跟踪源码被拒、运行目录/用户数据不误报、超过 10 个未跟踪文件的提示数量。
- 真实行为：在仓库根目录临时创建未跟踪的 `_untracked_probe.py`，执行 `scripts/package_delivery.py --output work/delivery_probe.zip`，退出码 2，提示“存在未跟踪文件……`_untracked_probe.py`”，`work/delivery_probe.zip` 未生成；随后删除探针，工作区恢复干净。

### 4.4 限制

- 检查依赖 Git 索引和 `.gitignore`：被明确忽略的文件不会阻塞打包，这是有意设计；忽略规则本身仍是交付契约的一部分。
- 未跟踪的私有配置（如 `.env`）通常已被忽略，不会触发该门禁；已跟踪的 `.env`/`.mcp.json` 仍由既有 `source_allowed` 拒绝。
